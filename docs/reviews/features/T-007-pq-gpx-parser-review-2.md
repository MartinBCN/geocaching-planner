## Software Architect review: T-007-pq-gpx-parser.md

**Member verdict:** Approve with changes
**Rationale:** The ticket follows ADR-0003 and the layering rules, but it leaves five gaps that will likely cause rework in T-008 or T-022: the async shape of the protocol, the result and warning type, the "found" identity, waypoint linking while streaming, and an `lxml` dependency that no ADR covers.

### Findings
| ID | Severity | Location & evidence | Issue | Recommendation |
|---|---|---|---|---|
| ARC-1 | Major | Scope/In: "`CacheSource` protocol, `iter_caches() -> Iterator[CacheParseResult]`" | The protocol is synchronous, but the backend is async (spec §9.3: "Async DB access (`asyncpg`)"). If T-008 iterates it inside an async endpoint, parsing 5,000 caches (up to 5 s, AC7) blocks the event loop. A future Geocaching.com API source (IMP-8, API-1) would make HTTP calls, so it could not fit a sync iterator without blocking or a redesign. This makes the abstraction harder to change later. | Define the protocol as `def iter_caches(self) -> AsyncIterator[CacheParseResult]`. Have `PocketQuerySource` run its sync `lxml` work in a thread (e.g. `anyio.to_thread`). Or keep it sync and state in the protocol docstring that callers **must** run it off the event loop. Either way, record the choice here so T-008 does not guess. |
| ARC-2 | Major | Scope/In: "(success or error with context)" vs. "unknown values go to `Other`, with a warning" and "Orphan waypoints are reported as warnings" | `CacheParseResult` has two variants (success, error), but the ticket also produces warnings. No warning channel exists. There is also no `ImportRun` field for warnings (spec §7 lists only `errors` (jsonb)), and IMP-6 lists only errors in the summary. This type crosses the port boundary, so if it is decided late, T-007 and T-008 both have to change. | Define the type in `services/ports.py` (or `domain/`) now, e.g. `CacheParsed(cache, warnings: list[ParseIssue])` and `ParseError(issue: ParseIssue)`, with `ParseIssue(file, line, gc_code, code, message)`. ### Strengths
- Errors are reported per entry and parsing continues (AC3/AC4). The user's whole PQ import doesn't fail because of one bad cache, as IMP-7 requires.
- HTML descriptions and Unicode are kept byte-exact, and sanitizing happens at render time (AC6). Cache pages with local-language text stay faithful to the original.
- Large PQs are covered (AC7: 5,000 caches in under 5 s), which matches how GSAK users import several overlapping PQs at once.

### Open questions for the author
- Geocaching.com PQs may write the user's corrected coordinates (set on the website) into `<wpt lat/lon>` in place of the posted ones. Should the parser detect or flag this, given CAC-5's "the original coordinates are kept and still visible"?
- Overlapping PQs in one upload often contain the same GC code more than once. Should the parser yield duplicates, or pick one (for example, the most recent file or log date)? Who decides what the summary counts?
- How should non-GPX entries inside a ZIP (a readme, or a ZIP holding several PQs) be handled: skip them silently, warn, or treat them as a file-level error?

- The ticket has no `Reviews:` line (TEMPLATE) and is already `Ready` without a council report. This is a process question for QDE.
- Unit tests that read fixture files from disk may conflict with spec §9.2's "No I/O" for unit tests. Wall-clock and memory thresholds in CI may also be flaky (QDE).
