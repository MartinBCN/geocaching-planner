## Top actions
1. Define the error contract precisely: a `Problem` pydantic model (`type`, `title`, `status`, `detail`, `instance`, plus a named `errors` field-error list for 422), registered as `application/problem+json` in OpenAPI, with exact ACs for 404/422/500. Register the handler on `starlette.exceptions.HTTPException`, and make the 500 AC testable (`raise_app_exceptions=False`, no secret/Traceback in body, one captured error log event). (#1, #6, #19; ARC-1, PRD-1, QDE-1, QDE-2, QDE-9)
2. Make the settings object the only source for host/port: name the fields (`host`, `port`, `log_json`), add a run entry point that `dev` uses, add ACs for defaults and overrides, and isolate tests from `.env`/`GCP_*`. (#4; ARC-6, PRD-5, QDE-3)
3. Establish the layering patterns later tickets copy: a framework-free `DomainError` hierarchy mapped to problem+json in `api/`, plus an automated layering test (or ruff banned-imports) with its own AC. (#2, #3; ARC-2, ARC-3)
4. Rename `logging.py` (ruff A005 conflict) and add ACs/tests for the structlog JSON/console renderer switch. (#5, #7; ARC-4, QDE-5, QDE-4)
5. Give AC6 and the Python 3.14 check objective verification: AC6 is manual until T-005 and must show the gates fail when violated; add an AC and an explicit stop protocol (Completion notes, `Status: Blocked`, no `mise.toml` change) for 3.14 incompatibility. (#8, #9; QDE-6, QDE-7)

## Product Designer review: T-002-backend-skeleton.md

**Member verdict:** Approve with changes
**Rationale:** This infrastructure ticket only moves the main user flow forward indirectly, which is fine for M0. But the error contract it sets will shape every user-facing error message and form validation state later, so it needs a clearer definition.

### Findings
| ID | Severity | Location & evidence | Issue | Recommendation |
|---|---|---|---|---|
| PRD-1 | Major | Acceptance criteria: "AC3: A validation error returns 422 problem+json with field errors." | The ticket doesn't define what a field error looks like. Later forms need to point the user at the exact input that failed and say why. Examples are corrected coordinates and coordinate entry (CAC-5, RTE-1), home location (CAC-6) and corridor width (CAR-1). The ticket says it "sets the patterns that every later ticket copies", so an ad-hoc shape will likely cause rework in the frontend error states. | Rewrite AC3: "A validation error returns 422 problem+json with `errors: [{"field": "<dotted path, e.g. body.lat>", "message": "<human-readable>"}]`, where `field` names the request field without the `body`/`query` location prefix." Document the shape in the OpenAPI schema so the generated client types it. |
| PRD-2 | Minor | Acceptance criteria: "the fields `type`, `title`, `status`" | Requirements like RTE-7 ("the user gets a clear error") and IMP-7 ("fail with a clear error") will show the problem body in the UI. | PRD-3 | Minor | Scope/In: "500 without leaking internals" plus "the error is logged" | For a single user running locally, a generic 500 message in the UI can't be matched to the log line in the `mise run dev` console. | PRD-4 | Minor | Scope/In: "Add the backend variables to `.env.example`." | NFR-4 requires a *documented* `.env.example`.
